High-Level Architecture Overview

Overview

The Inventory Recovery Management System (IRMS) is designed as a decoupled, multi-tier, offline-first Web Application. It combines a zero-latency Single Page Application (SPA) frontend running directly in client browsers with an asynchronous cloud persistence backend powered by Google Apps Script (GAS) and Google Sheets.

Core Architectural Layers

  • Presentation Layer — Modular Vanilla JavaScript UI components compiled with Vite, using responsive CSS and state-driven DOM rendering.
  • Client Persistence Layer — IndexedDB embedded database and Cache Manager maintaining local operational and reference data for zero-latency UI operations and offline support.
  • Transport Layer — HTTP REST API protocol executing asynchronous fetch calls with JSON payload structures between client engine and backend endpoints.
  • Application Server Layer — Google Apps Script (GAS) web application (`Code.gs`) executing modular route controllers, validation rules, and atomic execution locks.
  • Data Storage Layer — Relational database schema implemented across 13 dedicated worksheets inside a centralized Google Sheets Spreadsheet.

Client Component Architecture

Overview

The client application is built as a single-page application structured into decoupled module components under src/components/. Each component handles view rendering, local state management, user event listeners, and interaction with db.js.

Login Component
src/components/login.js

Renders credential login form, validates staff passwords against local reference cache, initiates 4-hour session timer, and triggers initial sync.

Request Pickup Component
src/components/requestPickup.js

Manages pickup request creation form, handles SKU code auto-fill from product catalog, generates ticket IDs, and renders user ticket history.

Picking Task Component
src/components/pickingTask.js

Renders waiting task list, manages multi-item selection state, executes swipe-to-confirm modal, and handles rack putaway modal workflow.

Stock Movement Component
src/components/stockMovement.js

Renders transfer and deduction task queues, executes 2-step verification modal (SKU scan match + location target), and updates movement status.

Stock on Hand (SOH) Component
src/components/soh.js

Renders real-time inventory dashboard, calculates summary KPIs, provides SKU/category/rack filtering, and triggers stock deduction requests.

Admin Master Data Component
src/components/admin.js

Restricted to Super role. Provides CRUD interfaces for managing staff accounts, warehouse zones, rack locations, and checker lines.

Data & Offline-First Engine Architecture

Overview

IRMS uses an Optimistic Offline-First Architecture. All read and write operations are executed against the local IndexedDB instance in 0ms, allowing immediate UI updates. Data changes are queued and synchronized with Google Sheets asynchronously in the background.

Caching & Sync Rules

Data CategoryStorage StoreTTL / Refresh StrategySync Triggers
Operational Collections (Requests, Tasks, Movements, SOH) IndexedDB Operational Stores Stale-while-revalidate (60-second background re-fetch threshold) Section navigation, form submission, manual sync button click
Master / Reference Data (Products, Racks, Zones, Users, Lines) IndexedDB Reference Stores Session TTL (persists for active shift session) Session startup login, manual full resync action
Session State (User, Role, Expiry) Browser LocalStorage 4-Hour Shift Expiry Login success, logout, session expiration interval check

Security & Authentication Architecture

Security Model

Security is enforced across both client execution and backend request validation layers:

  • Client Session Security — Authenticated staff sessions are encrypted and stored in local storage with a 4-hour expiration timestamp. A background interval timer validates session validity every 15 seconds.
  • Role-Based Access Control (RBAC) — UI components dynamically hide or show feature routes based on staff roles (`Super`, `Staff/Checker`, `Picker`).
  • Input Sanitization — Client utilities (`src/utils/security.js`) scrub user form input to prevent XSS script injection before storage or transmission.
  • Backend Execution Locking — Concurrency protection via Google Apps Script `LockService.getScriptLock()` prevents race conditions during simultaneous stock edits.

Backend Controller & Lock Architecture

Overview

The backend application logic is implemented in Google Apps Script inside gas/Code.gs. It operates as a web app receiving HTTP GET/POST requests and executing controller functions mapped to 22 action parameters.

Backend Route Controllers (22 Actions)

CategoryAction NameDescription & Operation
Bootstrap getInitialData Fetches product DB, racks, zones, users, and checker lines in a single JSON payload.
Requests getRequests, createRequest, updateRequestStatus Queries, appends, and updates pickup request records in Request_Checker sheet.
Picking & Putaway getPickingTasks, startPickingTasks, completePutaway Manages picking state transitions, putaway logs, and atomic SOH increments.
Stock & Movements getSOH, updateSOH, getMovements, createMovement, completeMovement Handles inventory counts, double verification transfers, and stock deductions.
Lost & Found getLostAndFound, createLostAndFound Logs stray inventory entries and enqueues tasks into picking waiting list.
Admin Management getUsers, saveUser, deleteUser, getZones, saveZone, deleteZone, getRacks, saveRack, deleteRack, getCheckerLines, saveCheckerLine, deleteCheckerLine Executes master reference data CRUD operations on administrative worksheets.

Container & Deployment Infrastructure

Overview

IRMS is packaged for production deployment using Docker and Nginx, serving the optimized static assets built by Vite.

Deployment Stack Components

  • Build Engine — Node.js environment compiling ES modules and CSS assets into static distribution files in dist/ using Vite (`npm run build`).
  • Web Server — Nginx (`nginx.conf`) configured for SPA routing, fallback rules, and gzip static asset compression.
  • Container Runtime — Docker containerized deployment runtime managed via `Dockerfile`.
